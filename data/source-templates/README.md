# Source-system CSV templates

CSV templates for loading test data into the simulated customer systems: TrackWise Digital, Veeva Vault QMS, Teamcenter,
Windchill, SAP S/4HANA, Oracle ERP, MES, LIMS, the risk management file, Coupa and Salesforce Service. MDARIX then
pulls the data from those systems through its connectors, the way it will with a real customer.

Each folder is one application. Each file is one kind of record in that application, and its columns are named the way
that system names them (SAP uses its technical names such as `MATNR` and `CHARG`). Matching these names to MDARIX
fields is the job of the mapping sheets in Mapping Studio.

`_data_dictionary.csv` lists every column with:
- its meaning and data type;
- whether it is required;
- the MDARIX field it maps to;
- whether MDARIX imports it today.

The templates are generated by `scripts/generate_source_templates.py`. Change that script, not the files, then run
`python scripts/generate_source_templates.py`.

## The example data tells one story

All files share one synthetic story, so you can see how MDARIX links records across systems:

- **AquaFlow 200 infusion pump**, `PUMP-200`, in revisions C and D:
  - product and BOM data in Teamcenter;
  - materials, batches and suppliers in SAP;
  - complaints in TrackWise;
  - production in the MES;
  - tests in the LIMS;
  - risks in the risk file.
- **The problem:** Revision D (change `ECN-4471`) lowered the occlusion threshold and moved to sensor revision B. Lots `L24-0815` and `L24-0902` used sensor lot `KS-5521` from Kestrel Sensors. That sensor lot failed a drift test (`TR-88120`), and complaints `CMP-10021`, `CMP-10022` and `CMP-10024` report false occlusion alarms.
- **AquaFlow 300 ambulatory pump**, `PUMP-300`, shows a second technology stack: Windchill, Oracle ERP and Veeva QMS.

Replace the example rows with your own data and keep the header row exactly as it is.

## Rules for every file

- UTF-8, comma-separated, one header row. Wrap a value in double quotes if it contains a comma.
- Dates as `YYYY-MM-DD`; date-times as `2026-09-11T11:30:00Z` (UTC).
- Yes/no columns as `Y` or `N`. SAP flags are `X` or empty.
- **Use the same numbers in every system.** The product, lot, component and supplier numbers must match across files: this is how MDARIX links a complaint to its lot, its components and their suppliers.
- **No personal data.** MDARIX refuses rows containing email addresses, phone numbers, personal names, patient identifiers or dates of birth. For people, use user IDs such as `QE-INV-014`.
- Don't start a value with `=`, `+` or `@`; MDARIX refuses spreadsheet formulas.

## How the data reaches MDARIX

Load the files into the simulated systems and connect MDARIX to them: see
`docs/runbooks/CUSTOMER_SOURCE_SYSTEMS.md`. Every record type here has an **MDARIX standard mapping**
(`backend/app/access/standard_mappings.json`). Mapping Studio offers it as **Use the standard mapping**.

- Files that mix kinds of records have one standard mapping per kind. Each keeps only its own rows with a filter:
  - Teamcenter `items.csv` (`item_type`)
  - SAP `materials.csv` (`MTART`: `FERT` products, `ROH`/`HALB` components)
  - Oracle `items.csv` (`ITEM_TYPE`)
  - Windchill `parts.csv` (`part_type`)
  - Veeva `quality_events.csv`: only `Complaint` events become complaints.
- A few records get a fixed value for a field their system does not carry. For example, LIMS results are evidence
  of type "Test result".
- Columns marked "No MDARIX field yet" in the dictionary are kept in the source system but not imported. These are
  supplier risk assessments, and details such as quantities, units and expiry dates.

Three things to know about the import:
- Each products file needs the product name on every row, so the revision files repeat it.
- A batch with one bad row imports nothing. `batches.csv` therefore holds finished-product batches only; component
  batches such as sensor lot `KS-5521` appear in the genealogy files.
- Records that refer to others need those loaded first. The runbook gives the order.
