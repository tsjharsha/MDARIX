## 1. Purpose, in plain words

A customer's QA must be able to do three things before and after go-live:

1. **Audit MDARIX as a supplier** and decide it is fit (supplier pack, Part 11 / Annex 11 assessment, hosting assessment, SOPs, trust facts).
2. **Rely on MDARIX's validation of each release** and only validate its own use (VMP, risk assessment, GAMP justification, per-release pack: URS, FS/DS, RTM, IQ/OQ/PQ, deviations, VSR, signed release approval).
3. **Run its own intended-use validation and keep the system in a validated state** (UAT/PQ, migration, periodic review, go-live checklist; recovery validation and a monthly health report from MDARIX).

B6b is mostly documents. The code is small: one generator for the per-release pack, two scripts (recovery check, health report), one test hook, and test tags. No screens, no migration, no switches.

## 4. Where the documents live and how they are made

- **Place (⚑ D2):** the product repository, `docs/validation/` (MDARIX documents, sources and signed PDFs) and `docs/validation/releases/<version>/` (per-release records). Versioned with the code and tagged with each release. Customers' filled copies never go into the repository.
- **Sources are text** (Markdown, CSV, JSON), so every change shows in a diff. Word and Excel files are generated from the sources at a tag; the generator fixes the document dates so the same tag gives the same file.
- **Formats (owner, 11 Nov):** Word (DOCX, python-docx, E19) and Excel (XLSX, a small standard-library writer, D12) for customers to load into their own tools; PDF for the signed copy (D13).
- **Signing (⚑ D6):** a signed PDF. Its SHA-256 is recorded in `docs/validation/signatures.csv` (document ID, version, signer, role, meaning, date, SHA-256) and committed. MDARIX's own e-signature is not used for MDARIX's own documents.
- **Write-once:** the generator refuses to write into a release folder that holds a signed approval (B6-50). A correction is a new version that names the one it replaces.
- **Writing standard** (VMP annex): purpose and scope first; "shall" for requirements, never "may/should/probably"; one requirement per statement, each testable; every requirement traced to a test and evidence; plain English, short sentences; a final quality review of consistency, numbering, references and signatures; each document's header: ID, title, version, status, author, reviewer, approver, date, code baseline, change history.
- **Document IDs:** MDX-VAL (validation), MDX-SUP (supplier), MDX-SOP, MDX-OPS (operational records), MDX-CUS (customer templates). MDX-B10-003 and -004 are marked "superseded by MDX-VAL-001 / -002"; MDX-B10-001, -002, -005, -006 stay and are referenced.
